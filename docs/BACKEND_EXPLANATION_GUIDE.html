1. Introduction & The Core Business Problem

Welcome! To understand this backend codebase easily, we first need to understand what real-world business problem this software solves.

1.1 Real-World Analogy: Study Center vs Traditional Library

📚 Important Concept: We Don't Lend Books, We Rent Desks!

In traditional college or public libraries, people borrow books and return them after a few weeks. However, this software is built for Study Centers / Reading Rooms (common for students preparing for UPSC, SSC, NEET, JEE). These facilities do not lend books. They have 100 physical study desks (Desk #1 to #100) with air conditioning, Wi-Fi, and power sockets. Because real estate rent is expensive, the owner rents out the SAME physical desk to different students during different times of the day!

1.2 The Canonical Shift Model

The facility runs 7 days a week, from 07:00 AM to 11:00 PM (16 hours every day). Time is partitioned into 4 non-overlapping shifts:

Shift Name Operating Window Minute Range [Start, End) Daily Duration Default Fee
Morning 07:00 AM – 11:00 AM [420, 660) 4 Hours ₹800 / month
Afternoon 11:00 AM – 03:00 PM [660, 900) 4 Hours ₹800 / month
Evening 03:00 PM – 11:00 PM [900, 1380) 8 Hours ₹1,200 / month
Full Day 07:00 AM – 11:00 PM [420, 1380) 16 Hours ₹2,200 / month

1.3 The Nightmarish Problems of Traditional Paper Registers

When study center owners manage this using paper registers or Excel sheets, disaster happens:

  • Double-Booking Desks: Two receptionists accidentally book Desk #15 for the Morning shift to two different students.
  • Full Day Collisions: Student A takes Full Day on Desk #20. But a staff member forgets and books Student B on Desk #20 for the Evening shift. Both show up at 5:00 PM and fight for the chair!
  • Expired Students Sneaking In: Subscriptions expire, but the front desk doesn't know who has expired today.
  • Financial Drifts: Students pay partial fees, and the owner loses track of who owes how much money.

Our FastAPI Backend was engineered to solve every single one of these problems with mathematical certainty!

2. Architecture Pattern: The 4-Layer Separation

To make the backend bug-free, scalable, and easy to maintain, we followed the industry-standard Layered Clean Architecture. Code is never mixed together. Instead, every responsibility is assigned to a specific layer.

1
HTTP & Routing Layer (backend/app/api/v1/endpoints/)
The Reception Counter: Receives incoming HTTP requests from React or Streamlit, checks the user's login token, unpacks URL parameters, and passes data to the Service Layer.
2
Schema Validation Layer (backend/app/schemas/)
The Security Inspector (Pydantic): Validates that incoming data is clean (e.g. mobile number is digits, seat number is between 1 and 100, dates are valid). If data is wrong, it rejects it immediately before hitting the database.
3
Domain Service Layer (backend/app/services/)
The Core Brain & Business Logic: Contains all intelligent rules! Checks seat availability, prevents double booking using locks, calculates discounts, and coordinates multiple database actions atomically.
4
Repository Layer (backend/app/repositories/)
The Storekeeper (Data Access): Executes pure SQLAlchemy database queries (SELECT, INSERT, UPDATE). It doesn't know about HTTP or web requests—it only talks to tables.
5
Database Model Layer (backend/app/models/)
The Blueprints (SQLAlchemy ORM): Defines the physical tables in PostgreSQL/SQLite (Seats, Students, Memberships, Payments, Attendance).

3.5 The backend/app/repositories/ Directory (Database Storekeepers)

These files write the raw SQL queries so the rest of the application remains clean and decoupled:

  • repositories/base.py: Provides generic, reusable CRUD helpers (get, get_multi, create, update, remove) that all repositories inherit from.
  • repositories/student_repository.py: Searches students by name, mobile, email, or code with case-insensitive ilike filters.
  • repositories/seat_repository.py: Fetches physical seats filtered by active/maintenance state.
  • repositories/membership_repository.py: Finds active memberships covering a specific date range, calculates financial balance (total fee − total paid = pending due), and handles pagination.
  • repositories/payment_repository.py: Queries transactions, computes daily collection totals, and filters by membership or date.

3.6 The backend/app/services/ Directory (The Brain of the System)

This is where the true intelligence of the software lives.

1. services/allocation_service.py (The Anti-Collision Engine)

This is the most critical service in the entire study center management system. It prevents double-booking using interval mathematics:

  • check_seat_availability(): When someone wants to book Desk #10 for Morning shift between Oct 1 and Oct 31, this function checks every active membership on Desk #10. If an existing student has booked Morning or Full Day on those dates, it says False and blocks the booking!
  • check_student_time_conflict(): Prevents a student from holding two different desks at the exact same hour of the day.
  • get_daily_seat_matrix(): Generates the live status of all 100 desks for the interactive seat grid on the frontend.

2. services/membership_service.py (Atomic Admission & Row Locking)

Coordinates student admissions, renewals, and cancellations safely:

  • Pessimistic Row Locking (SELECT ... FOR UPDATE): When two receptionists try to book Desk #1 at the exact same millisecond, the first request locks row #1 in the database. The second request is made to wait until the lock releases, completely preventing race conditions!
  • Atomic Transactions: Creating the membership and recording the initial cash/UPI payment happen in a single database transaction. If recording the payment fails, the membership creation is automatically rolled back!
  • Clean Renewal Lineage: When renewing, it links the new membership to the old one using renewed_from_id, maintaining student historical continuity.

3. services/payment_service.py (Financial Ledger & Voiding)

Enforces strict accounting rules:

  • Generates unique sequential receipt numbers: RCP-YYYYMMDD-XXXX (e.g. RCP-20261009-0001).
  • Never Deletes Records: If a cashier made an error entering a payment, the admin cannot delete the row. Instead, the admin must call void_payment() with a mandatory audit reason. The transaction status changes to VOIDED and the fee balance automatically reopens!

4. services/analytics_service.py (Executive KPI Calculations)

Computes the 3 multidimensional capacity metrics:

  • Physical Seat Utilization Rate: (Occupied Desks / 100) * 100
  • Slot-Capacity Occupancy Rate: (Booked Slots / 300) * 100 (Full Day counts as 3 slots; Morning, Afternoon, Evening count as 1 slot).
  • Time-Weighted Seat-Hour Rate: (Booked Seat Hours / 1,600) * 100

4. Step-by-Step Code Flow: A Real Life Example

Let's walk through an actual transaction to see how data flows through these files in real life!

👨‍🎓 Real Scenario:

Student "Rahul Sharma" walks up to the front desk. He wants to book Desk #10 for the Morning Shift from Oct 10 to Nov 09. He pays ₹800 in Cash upfront. Receptionist clicks "Execute Admission & Confirm Desk".

1
Browser Sends HTTP POST Request
React sends: POST /api/v1/memberships with JSON payload: {"student_id": "...", "seat_id": 10, "shift_id": 1, "start_date": "2026-10-10", "end_date": "2026-11-09", "initial_payment_amount": 800, "initial_payment_method": "CASH"} along with the JWT Bearer Token.
2
Security & Validation Layer Intercepts
core/security.py verifies the JWT token. Then schemas/membership.py (MembershipCreateSchema) verifies that start date is before end date, seat is between 1 and 100, and initial payment method is valid.
3
Endpoint Hands Off to MembershipService
api/v1/endpoints/memberships.py receives the request and calls membership_service.create_admission_atomic().
4
Database Row Lock & Availability Check
membership_service.py issues a SELECT ... FOR UPDATE on Seat #10 to lock the row. Then it calls allocation_service.check_seat_availability(). The allocation service queries existing memberships covering Oct 10–Nov 09. If another student already has Desk #10 in the Morning, it rejects with ConflictException("Seat already booked")!
5
Student Simultaneous Collision Check
The service calls allocation_service.check_student_time_conflict() to verify Rahul doesn't already hold another desk during morning hours.
6
Membership Created & Payment Stamped in Ledger
The service creates the Membership record. Since Rahul paid ₹800 cash, it generates sequential receipt number RCP-20261010-0015 and creates a Payment record with status COMPLETED.
7
Transaction Committed & Enriched Response Returned
db.commit() saves everything safely to disk. The endpoint formats the response with derived status ACTIVE, total_paid: 800.00, due_amount: 0.00, and returns HTTP 201 Created to the browser!
